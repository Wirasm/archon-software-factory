# Scratch a node made is released when the node ends, not only when the run ends

## Desired outcome

Scratch a node made for its own work is gone when that node's work ends, with its git worktree registrations, and no workflow has to carry a cleanup step to get that. A long run's disk use is bounded by what its running nodes need, not by everything every earlier node left behind.

## Problem

The engine removes a run's scratch directory (`$ARTIFACTS_DIR/.archon/scratch/`) once, when the run ends (`packages/workflows/src/run-scratch.ts`). Inside a run nothing releases it. A workflow whose nodes each make a scratch worktree and install dependencies in it therefore has to prune between rounds itself.

The bundled SDLC pack does exactly that: `.shared/scratch.ts`, `review/scripts/prune-scratch.ts` and `simplify/scripts/prune-scratch.ts` (102 lines, two workflow nodes, a conformance test that holds the pack's copy of the scratch path to the engine's) re-implement the engine's "remove worktrees under scratch by path, then the files" at the end of every review round.

Measured on the maintainer's install, from the `node_completed` events of 5,679 `prune-scratch` nodes in 2,227 runs between 2026-10-06 and 2026-11-13:

- A review round removed 0 to 6 scratch worktrees (0: 1,150 rounds, 1: 1,109, 2: 1,308, 3: 423, 4: 86, 5: 91, 6: 8). Simplify removed 0 to 2.
- A whole run made 2.74 worktrees on average and 21 at most. 575 runs made 4 or more, 196 made 8 or more, 37 made 12 or more.
- One surviving lens worktree of this repository with dependencies installed is 717 MB (674 MB of it `node_modules`). Only one sample exists, because scratch is deleted.

So with the pack's pruning, a run holds at most about 6 worktrees (roughly 4 GB here). Without it, the same runs would hold their whole total until they end: about 2 GB for a typical run, about 6 GB or more for one run in eleven, and about 15 GB for the largest. Several build runs execute at once.

## Why it is worth solving

- A full disk has killed runs on this install before: processes exit and their rows stay `running`.
- The pack cannot drop its own copy of engine cleanup until this holds (tracker issue 4438, which cuts the pack back to what it delivers). The deletion is otherwise mechanical.
- Any workflow that fans out read-only reviewers or probes meets the same choice: write a cleanup node, or let scratch grow for the length of the run.

## Why now

The pack cut is in progress and this is the first deletion it wanted to make on a shipped primitive. The measurement above says the run-end cleanup alone is not enough for it.

## Invariants

- Scratch a later node still needs is not removed under it. If the engine cannot know that, the author declares the scope; the engine does not guess.
- Only worktrees under the run's scratch are deregistered, by path. No `git worktree prune`, and never the run's checkout or another run's worktree. This is what run-end cleanup does today.
- Run-end cleanup stays as it is, as the backstop for a node that died.
- A paused or resumed run does not lose scratch a node is still using, and a resumed run still starts without stale scratch.
- No new YAML field unless it passes the workflow-language admissibility test. A workflow variable for a node-scoped scratch directory, like `$ARTIFACTS_DIR`, adds no field.
- A release that fails is logged and does not fail the node.

## Acceptance

- An engine fixture: a loop of three iterations whose body node creates a git worktree under its scratch and writes a large file there. After each iteration ends, the worktree is deregistered and its files are gone; the run's scratch does not grow across iterations.
- A node that fails or is cancelled mid-way leaves nothing behind once the run ends, as today.
- Scratch a workflow puts in the run-wide directory behaves exactly as today.
- With this in place the SDLC pack's three scratch files and two `prune-scratch` nodes can be deleted with no change in peak disk use. That deletion is a separate pack pull request.
- The variables reference documents the scope and when each kind of scratch is removed.

## Solution steering (optional)

One shape that fits: a per-invocation scratch directory the engine creates under the run's scratch and hands to the node as a variable, removed when the invocation reaches a terminal state, using the same worktree deregistration as run end. The pack's lenses already work under `scratch/<lens>/`. It is a suggestion; the outcome above is what matters.

Refs #4438. Related: #5535 (finished runs' data is never removed).
