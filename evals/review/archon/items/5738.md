# A sandbox's network and filesystem keys that Archon's schema does not list, such as deniedDomains, are dropped without a warning

## Problem

A node's (or a workflow's) `sandbox:` block is parsed by `sandboxSettingsSchema` in `packages/workflows/src/schemas/provider-options.ts`. The top level is `.passthrough()`, but the nested `network:` and `filesystem:` objects are plain `z.object(...)`, so zod strips every key they do not list. The parsed object is what reaches the Claude SDK (`options.sandbox = nodeConfig.sandbox` in `packages/providers/src/claude/node-config.ts`).

The Claude Agent SDK that Archon depends on (`@anthropic-ai/claude-agent-sdk` 0.3.302) accepts more keys than Archon lists:

- `network`: `deniedDomains`, `strictAllowlist`, `allowMachLookup`, `tlsTerminate`
- `filesystem`: `allowRead`, `allowManagedReadPathsOnly`, `disabled`

All of these are dropped. `archon validate workflows` reports the workflow as `ok`, and the unknown-key warnings skip `sandbox:` on purpose: the reference says "`sandbox:` passes unknown keys through", and the comment in `packages/workflows/src/schemas/dag-node.ts` says "unknown keys are preserved, not dropped". That holds for the top level only.

## Why

The dropped keys are restrictions. An author who writes `deniedDomains: [evil.example]` or `strictAllowlist: true` gets a sandbox that is more open than the one they wrote, and nothing tells them.

`direction.md §schema-width` asks that capability mismatches "warn loudly, never silently no-op".

## Desired outcome

A key written under `sandbox.network` or `sandbox.filesystem` either reaches the SDK or is reported at load.

## Acceptance

- [ ] A node with `sandbox: { network: { deniedDomains: [x], strictAllowlist: true }, filesystem: { allowRead: [y] } }` passes those keys to the SDK, or `archon validate workflows` names each dropped key.
- [ ] The reference's sentence about `sandbox:` passing unknown keys through matches what happens to nested keys.

## Evidence

### Reproduction

Parsing with the schema from the pinned revision (the schema file is identical on `dev` at `40e531e7b`):

```ts
sandboxSettingsSchema.parse({
  enabled: true,
  network: { allowedDomains: ["github.com"], deniedDomains: ["evil.example"], strictAllowlist: true },
  filesystem: { allowRead: ["/x"], denyRead: ["/y"] },
  credentials: { files: [] },
})
// => {"enabled":true,"network":{"allowedDomains":["github.com"]},"filesystem":{"denyRead":["/y"]},"credentials":{"files":[]}}
```

The top-level `credentials` survives (passthrough); `deniedDomains`, `strictAllowlist` and `allowRead` are gone. A workflow with the same `sandbox:` block on a node validates as `ok` with no warning.

### Environment

- Archon version or commit: run on `442c90f10`; the schema is unchanged on `dev` at `40e531e7b`
- Platform or adapter: CLI
- Database: SQLite
- OS: Linux

## Constraints and related work

- Related issues or PRs: #1799 (the earlier fix for workflow-level `sandbox` being dropped), #5735
- Our workaround: a wrapper around the Claude Code executable adds `strictAllowlist: true` itself.
- Solution steering: Hint — making the nested objects `.passthrough()` as well would match what the reference already says.
