# In an included workflow whose entry node is a script or bash node, the first AI node continues the caller's session

## Problem

The reference says "A composed workflow's entry node starts a fresh session, exactly as it would if you ran that file on its own". When the included workflow's entry node is a `script:` or `bash:` node, its first AI node does not start fresh: it continues the session of the caller's last AI node.

What the code does on `dev` at `40e531e7b`:

- `packages/workflows/src/include/inline.ts` marks `blockEntry` only on nodes with no `depends_on` inside the included workflow (`wasEntry`). A first AI node that depends on an entry script is not marked.
- `selectSession` in `packages/workflows/src/dag/nodes/agent/dispatch.ts` clears the sequential cursor only for a parallel layer, `context: fresh`, a node marked `blockEntry`, or a provider change.
- `advanceSequentialSession` in `packages/workflows/src/dag/run-layers.ts` leaves the cursor alone for a node without a session id, so the entry script does not clear it either.

Run on its own, the same file's first AI node has no cursor and starts fresh. Composed, it picks up whatever the caller ran last. This is the case the comment in `selectSession` (#1764) describes as the reason for the entry rule: "the same file behaving differently depending on who composed it".

## Why

The first AI node of the block starts with the caller's whole history, which the block's author did not write for and cannot see. Whether it does depends on whether the block happens to start with a script, which nothing in the YAML shows.

## Desired outcome

The first AI node an included workflow runs starts a fresh session, whatever kind of node the block starts with, unless it says `context: shared`.

## Acceptance

- [ ] In the reproduction below, `ask` does not see the caller's codeword.
- [ ] `context: shared` on that node still continues the caller's session.

## Evidence

### Reproduction

```yaml
# child
nodes:
  - id: prep
    bash: "echo ready"
  - id: ask
    depends_on: [prep]
    prompt: "If an earlier message in this conversation gave a codeword, reply with only that codeword. Otherwise reply NONE."
# parent
nodes:
  - id: first
    prompt: "The codeword is PINEAPPLE-42. Reply with only OK."
  - id: block
    include: child
    depends_on: [first]
```

Expanding the parent with `expandWorkflowIncludes` on `442c90f10` (`selectSession` is unchanged on `dev`; `inline.ts` differs only by #5550):

```
first         deps=[]              blockEntry=false
block__prep   deps=["first"]       blockEntry=true
block__ask    deps=["block__prep"] blockEntry=false
```

With an AI node as the child's entry instead, that node is marked `blockEntry=true`. We found this by reading the code while checking which session each of our AI nodes continues, and confirmed it with the expansion above. We have not run the live reproduction.

### Environment

- Archon version or commit: expansion run on `442c90f10`; the quoted lines are on `dev` at `40e531e7b`
- Platform or adapter: CLI
- Database: SQLite
- OS: Linux

## Constraints and related work

- Solution steering: Hint — mark the first AI node reached from the block's entry, or clear the cursor at the entry whatever its kind.
