# When a run on an item ends, the bound stage starts and waiting work is admitted

## Desired outcome

When a run on an item ends, two things happen with that end and need no other command:

- the stage bound to that outcome starts on the same item, with the ended run's result available as its input;
- a start already waiting for the capacity that run held is admitted.

No node in the ended run fires anything, and nothing has to be running besides the process that ends the run.

## Problem

Nothing in the engine reacts to a run's end. A pack that wants the next stage to start ends its workflows with a script that calls `archon trigger fire`, and every arrow between stages is hidden in that script. Queued starts move only when another fire arrives or someone runs `archon trigger drain` (#5665): in a measured backlog of 60 starts on a 5-slot resource, 34 sat queued with every slot free until a drain was run by hand.

This is the first half of #5650 (slice 4). The second half, a start when an item's asks are settled, waits for #5640. This half depends only on the item (#5627, merged).

## Why it is worth solving

It is what turns a set of stages into a factory. Today five stages of a pack are chained by a script outside the engine, and a hand-off can be lost or doubled by a crash between a run's end and the fire.

## Why now

It does not depend on #5632 or #5640, so it can be built beside them. It and #5640 both change the write that ends a run; this one goes first.

## Constraints from the project's own documents

Read `.archon/workflow-language-constitution.md`, `.archon/direction.md` (§user-owns-policy, §standalone-core, §load-time-composition) and the workflow triggers guide before planning. They bind this design:

- **Earn it on governance, not convenience.** A script can already fire the next stage, so admissibility question 3 puts the burden here: the case is that every hand-off is declared data the engine validates at load and any surface can draw, that a start caused by a run's end happens at most once across a crash, and that it goes through admission like any start. State that case.
- **A binding selects among static targets.** It maps a declared outcome value to a named stage, and data into that stage's declared inputs. No expression, and no value produced at run time names a stage. A named stage that does not exist is refused at load.
- **Bindings are deployment configuration.** The triggers guide says bindings "do not belong in workflow YAML"; a pack recommends them (`archon pack bindings`) and the deployment owns them. Say where this binding lives and who owns it.
- **Through the host seam.** Wakes and triggers are core surfaces a CLI command, a server loop or an OS timer drives. The process that ends a run is a host moment; this adds no always-on component. Say what happens when that process dies between the end and the start, and which host picks it up.
- **The engine does not decide policy.** It starts what the binding names. It does not rank, and it does not decide whether an item is ready.

## Open questions the plan must answer first

1. **What is the outcome a binding keys on?** The engine's `outcome` today is a boolean from `outcome_field:`, written before the run ends (#5660). A stage ends in one of a few named outcomes. This and #5640 need one declared result contract; state the smallest form of it this half needs, so #5640 can extend it and not replace it.
2. **How does the next stage read the ended run's result?** "The latest result of stage X on this item" is a reference to a recorded fact, like `$node.execution.checkoutStart`. Say what the reference is and where it resolves.
3. **Arrival order.** Starts caused by a run's end go through admission in arrival order, as today. Record the cause of each start (a run ended, and which) as a fact on the start, readable afterwards. No ordering rule.

## Invariants

- One start path: receipts, admission, capacity and the item of #5627. No second way to start a run.
- At most once: killing the process between a run's end and the next start, then starting it again, yields exactly one run of the bound stage.
- A run with no item, and a deployment with no such binding, behave exactly as today.
- An agent never names the next stage.
- Additive schema only, SQLite and PostgreSQL aligned. On the file store this is refused before a run starts, as items are (#2791 is not ruled).
- Engine fixtures only; no pack workflow in engine tests, and no change to the bundled SDLC pack.

## Acceptance

- A fixture with two stages and one binding: stage A ends with an outcome, stage B starts on the same item and receives A's result, and no node in A fires anything.
- Stage A run twice with different results: B receives the second.
- CLI only, capacity 2, six starts fired and then no further command: all six run to their end.
- A start by hand on a resource with free slots and nothing running is not refused as full or left waiting behind a queued start.
- The kill-and-restart case above.
- `archon workflow runs --item <key>` shows the runs in order, and each start's cause can be read.
- The binding and the reference are documented, and the constitution gains the case-law rows the design needs (as a proposal in the pull request; the operator edits that document).

Closes the run-ended half of #5650 and #5665.

## Discussion

**Wirasm**:

State on dev as of 2026-11-16, for whoever plans this:

- Open question 1 is answered by PR 5698 (issue 5660). A workflow declares `returns: { node, outcome }`; the outcome is a declared enum value or a boolean, and it is written once, by the write that completes the run, into `completed_outcome`. A binding keys on that value. Do not add a second outcome.
- Reading an item's runs in order exists: `archon workflow runs --item <key>` and `GET /api/items` (PR 5707). The cause of a start is the new fact this issue adds to that read.
- Resume by run id continues a killed run (PR 5717).
- Issue 5640 (asks in a run's result) changes the same completing write and is built after this one.
