# Recreating the event log can acknowledge unread events

Filed by Wirasm.

<!-- archon-discovery recreated-event-log-skips-unread-events -->
## Problem

If events.jsonl disappears while the daemon remains running, the next event silently recreates it. An existing inbox reader can then commit a later sequence without receiving intervening person events. Restoring the original log does not make those events unread again.

## Evidence at the base

Verified by reading fb842e45cb7876733e469bb89882b1d42026fbf9; no tests or probes were run.

- src/store.rs:840-843 allocates increasing event sequences in memory.
- src/store.rs:858-862 opens events.jsonl with create(true) and append(true), allowing a missing log to be replaced by a file containing only the next event.
- src/store.rs:888-898 initializes an existing reader's position from its committed sequence, then raises through to every sequence found in the current file without checking for missing history.
- src/store.rs:915-924 persists that higher position.
- src/main.rs:852-856 commits the returned through position after writing the returned batch.

For example, a reader has committed sequence 1 and a person event at sequence 2 remains unread. Move the log aside while the daemon stays running, then produce sequence 3. The new log contains only sequence 3. Reading and committing the inbox advances the reader to 3 without delivering sequence 2. Restoring the original log still leaves sequence 2 excluded by the committed cursor.

## Why and why now

A temporary loss of the log becomes permanent loss of inbox delivery, even when the missing history is recoverable. This contradicts the retryable delivery intent recorded on issue #3. The base remains affected. Open PR #35 handles disappearance during indexed reads, but its create-on-append and committed-reader path retain this recreated-log case. Issue #12 concerns storage size and read cost; issue #45 and PR #50 concern warning-output failure. Neither covers this defect.

No dedicated project direction document was found. README.md describes inbox delivery as how agents hear the person's actions.

## Outcome

A recreated log must not allow inbox progress to acknowledge unavailable unread history. Detect the missing-history condition and report a recoverable failure until delivery can safely continue.

## Invariants

Preserve per-reader and per-project progress, non-consuming reads, explicit commits after successful output, monotonic event positions, and serialized mutations under the store lock. A genuinely new home must work without an existing event log. Do not require contiguous sequence numbers for a project, since unrelated events also receive sequences.

## Acceptance

- Cover an already committed reader with an unread person event, removal of the live log, and a subsequent mutation that would recreate it.
- The reader must not successfully acknowledge a position beyond the unavailable unread event; its persisted progress remains unchanged.
- Restore the original history and verify the same reader receives the previously unread person event and can then commit normally.
- Confirm a fresh home without events.jsonl still supports normal creation and inbox delivery.
- Pass cargo test and cargo clippy.
