# Two test fixtures read an accepted socket that inherits nonblocking mode on macOS

Filed by Wirasm.

<!-- archon-discovery sse-resync-fixture-nonblocking-read -->
## Problem

The `an_answer_is_reread_after_an_sse_resync` unit fixture can panic while reading an HTTP request, before exercising its resync assertion.

Verified by reading base `17601b65d95341dfaace017893839fb94f31ad3e`:

- `src/main.rs:1186-1189` creates the fixture and sets its listener nonblocking.
- `src/main.rs:1194-1202` retries `WouldBlock` while accepting connections.
- `src/main.rs:1203-1207` sets a read timeout on the accepted socket, then unwraps `read_line` without explicitly restoring blocking mode or handling `WouldBlock`.
- On macOS an accepted socket can inherit nonblocking mode. A read timeout does not restore blocking mode, so reading before request bytes arrive can immediately return `WouldBlock`.
- `src/main.rs:1228-1230` contains the intended answer/resync assertion, which the fixture failure prevents from being reached.

## Why and why now

This makes the unit suite intermittently fail because of fixture timing. The defective socket setup remains at the base. Tracker searches using resync, WouldBlock, flaky and nonblocking found no covering open issue or fixing pull request.

## Outcome

Read each accepted fixture connection in blocking mode with its existing bounded read timeout, so delayed request bytes do not cause an immediate `WouldBlock` panic.

## Invariants

Preserve bounded acceptance and read waits, the real SSE resync exchange, and the assertion that the answer is reread. Keep production waiting behavior unchanged.

## Acceptance

- Explicitly establish blocking mode before timed reads on accepted fixture sockets.
- Verify that a connection accepted before its request bytes arrive is read successfully once those bytes are sent.
- Run the focused resync test repeatedly on macOS and retain its answer assertion.

No separate project direction document was found; this repairs an existing verification fixture.

## Discussion


**Wirasm**:

Retargeting after a post-merge audit on 2026-11-12. The fixture this issue describes is gone: since PR 35 (`d159de2`), `an_answer_is_reread_after_an_sse_resync` (`src/main.rs:1286`) reads from a byte slice and opens no socket.

The same defect class is still live in two other test files:

- `tests/closed_pipe.rs:114` (PR 33) and `tests/pull.rs:142` (PR 41) set the listener nonblocking, accept, set a read timeout, then `read_line().unwrap()` (`closed_pipe.rs:68-73`, `pull.rs:159-161`).
- On macOS an accepted socket inherits `O_NONBLOCK`, and a read timeout does not clear it: a read before the bytes arrive returns `Err(WouldBlock)` after about 19 µs (checked with a small probe).
- It has failed a real run: a full validation stopped at `tests/closed_pipe.rs:73` with `WouldBlock`.

Fix: set the accepted stream blocking (`stream.set_nonblocking(false)`) before the read timeout, in both files. Acceptance: both tests pass 50 times in a row on macOS.
