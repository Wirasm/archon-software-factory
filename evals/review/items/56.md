# An open jelly wait --since misses every event after the event log is trimmed

Filed by Wirasm.

## Problem

A `jelly wait --since` that is already running misses every event written after the event log is trimmed. Without `--timeout` it never returns.

`wait_since_at_handoff` opens `events.jsonl` once (`src/server.rs:487-489`, `open_history` at `:470`), and `wait_for_record` reopens it only when the reader is `None` (`:546`). Since PR 35, `Store::log` trims the log once an append passes `LOG_LIMIT` (`src/store.rs:1110-1114`), and the trim replaces the file by write-then-rename (`write_atomic`, `src/store.rs:1367`, `:1504-1508`). The open wait keeps reading the old, unlinked file.

## Evidence

Reproduced on a build of `development` at `9359e5e` with a throwaway home: the log padded to 8,388,508 bytes; `jelly wait t:j --since seq:58739 --timeout 8` started; an agent `call` triggered the trim (the file's inode changed, size 4,194,190); a person's `call` followed at seq 58741. The open wait printed "nobody changed t:j in time" and exited 2. A fresh wait at the same `--since` printed the person's event at once. Found by a post-merge audit of PR 35.

## Why it matters

`jelly ask` tells the agent to run exactly this wait (`src/main.rs:1000`). An agent waiting for a person's answer on a busy jelly never hears it.

## Desired outcome

An open wait sees every event appended after it started, whether or not the log was trimmed in between.

## Invariants

- The trim stays (issue 12's size bound).
- No event is reported twice or skipped across a trim.

## Acceptance

- A test starts a wait, forces a trim, appends an event, and sees the wait return that event.
- The existing wait and trim tests still pass.

## Solution steering (optional)

Reopen the reader when the file at the path is no longer the one it holds (compare inode or file identity on each wake).
