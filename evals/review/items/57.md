# Store::sweep can poison the store lock when stderr is closed

Filed by Wirasm.

## Problem

`Store::sweep` prints with `eprintln!` while the hourly sweeper holds the store lock (`src/store.rs:810`, called under `sweeper.store.lock().expect("store lock")` at `src/server.rs:139`). If stderr is closed and an archive fails, `eprintln!` panics, the mutex is poisoned, and every later request that locks the store panics.

## Evidence

Found by a post-merge audit of PR 50, which fixed the same pattern in the event-log warning (issue 45) but not this sibling. Reachable only when both hold: a hand-run `jelly serve` whose stderr pipe closed (the auto-started daemon sends stderr to `/dev/null`, `src/startup.rs:113-115`), and a failing `set_archived`. The same preconditions as issue 45.

## Why it matters

One failed archive on a daemon whose terminal went away takes down every later request until restart.

## Desired outcome

A diagnostic write that fails never panics while the store lock is held.

## Invariants

- The warning is still shown when stderr works.

## Acceptance

- The same write pattern PR 50 used is applied here, with a test like PR 50's.

No comments.
