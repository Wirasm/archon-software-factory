# Repo worktree container isolation

Filed by buun-dev.

# Outcome

Allow an explicitly selected repo run to execute inside a container while using its own git worktree as the workspace. The container provides the execution boundary and toolchain; the worktree is nested inside it as the checked-out workspace.

This is an accepted product gap. The implementation must ship as one whole isolation backend, not as unused contract groundwork.

## Current gap

Archon currently supports these combinations:

| Codebase | Workspace | Execution |
|---|---|---|
| Repository | Git worktree | Host process |
| Folder project | Existing folder or container overlay | Host process or container |

A repository cannot currently combine a git worktree with container execution. This prevents repo workflows from using a pinned container toolchain and keeps concurrent runs dependent on the host environment.

## Accepted contract

The implementation must follow `direction.md §isolation-layers`, `§isolation-never-inferred`, `§isolation-arrives-whole`, and `§same-path-workspace`.

### Explicit selection

- Never infer or silently upgrade isolation from workflow shape, host platform, concurrency, or another field.
- The existing explicit isolation/configuration boundary must select container execution for a repo run.
- Unsupported or incomplete configuration fails before a run starts and names the setting the operator must correct.

### One complete backend

Land the backend, typed contract, routing, persistence, and lifecycle together in one PR. Do not first add optional `ExecutionContext` fields or helpers with no production producer.

The backend owns:

- creating or adopting the run's git worktree;
- mounting that workspace into the container;
- producing the execution context consumed by providers and deterministic nodes;
- pause/resume and process restart behavior;
- finalization, cleanup, and failure recovery;
- preserving the worktree/branch outcome needed for commits and pull requests.

The repo backend must not inherit the folder-overlay apply/discard gate. A repo run's durable output is its worktree and branch.

### Path ownership

Prefer mounting the workspace at the same path inside and outside the container. First verify whether running Archon on Linux or inside WSL provides the supported Windows path without divergent addressing.

If an accepted deployment still requires different host and container paths, resolve them once at run setup:

- Model host-visible and node-visible paths as distinct typed values.
- Require every engine-owned path used by the run to resolve: workspace, artifacts, logs, state, docs, provider working directories, and any other path exposed to nodes.
- Throw before execution when a required node-visible path is missing.
- Use the resolved node-visible value consistently in prompt/script substitution, subprocess environment variables, provider arguments, and Docker arguments.
- Keep the host-visible value for Archon-side persistence, artifact serving, cleanup, and other host operations.

Do not add a generic prefix `pathMap` that silently returns the host path on a miss. Do not remap strings independently in argv builders or other execution edges.

If naming the workspace boundary from #2490 is the smallest coherent type shape, fold or supersede that work within this complete backend rather than landing another producerless contract first.

### Execution boundary

- Container runs receive only the environment and per-user credentials Archon deliberately supplies. They must not inherit arbitrary host `process.env`.
- Existing provider capability checks remain fail-fast.
- Worktree isolation alone must not be described or treated as a security boundary; the container is the execution boundary.
- The design remains single-tenant per install and supports the acting user's credentials.

## Definition of done

- [ ] An explicitly configured repo run creates or adopts a dedicated git worktree and executes its AI, bash, and script nodes inside the selected container.
- [ ] The backend, execution contract, routing, lifecycle, and cleanup land together.
- [ ] Prompt/script substitutions, environment variables, provider arguments, Docker working directories, artifacts, logs, and state all use one consistent node-visible path for each engine-owned location.
- [ ] Archon retains the corresponding host-visible paths for persistence, artifact reads, cleanup, and branch/worktree management.
- [ ] Any required path that cannot be resolved fails before node execution with an actionable error.
- [ ] Pause, resume, detached/server execution, child workflows, cancellation, completion, and process restart preserve the same workspace and container ownership.
- [ ] Container execution does not inherit arbitrary host environment variables; acting-user credentials continue through the existing governed credential path.
- [ ] Cleanup never destroys a worktree or container still owned by an active run, and ambiguous cross-process ownership is surfaced rather than guessed.
- [ ] Focused unit and integration tests cover the backend lifecycle and every path-delivery channel. At least one real-container test proves dispatch through completion and artifact retrieval.
- [ ] Documentation explains explicit selection, supported host/container combinations, path behavior, lifecycle, security boundaries, and recovery.

## Out of scope

- Inferring container or worktree isolation.
- Landing a standalone kernel before its backend.
- A general-purpose path-rewriting facility.
- Replacing the existing folder-project overlay backend.
- Multi-tenant isolation inside one Archon install.

## Prior work and related issues

- #2207 explored the standalone `ExecutionContext` kernel and is closed because the backend and path contract must arrive together.
- #2490 tracks the unnamed workspace boundary that may inform the final type design.
- #2060 asks for coding agents inside Docker sandboxes.
- #2526 reports current container-isolation problems on macOS.

The next workstream should begin by tracing the current worktree and container lifecycle end to end, then prove the smallest same-path backend shape before introducing divergent addressing.

**Wirasm** (collaborator, 2026-08-21):

## Maintainer verdict

Short version: yes to the goal, no to the mechanism as proposed, and the kernel should not land on its own. Sorry this took a month to answer. You asked the right way, with a proposal before a PR, and you deserved a faster reply than that.

### What I'm saying yes to

A repo checkout that executes inside a container is a real gap. The table in your proposal is accurate: the git layer and the execution layer are only ever combined in two of the four useful ways, and the missing combination is the one that gives a repo run a pinned toolchain and keeps parallel dispatches off each other. You are not the only person asking for the shape either. #2060 asks for coding agents in Docker sandboxes, and #2526 is someone actively trying to get container isolation working today.

So the direction is welcome. I am not declining this on product grounds, and there is no `direction.md` clause against it.

### What I'm saying no to

Two things, and the second is the one that matters.

**The kernel does not land by itself.** #2207 adds an `ExecutionContext` field that nothing in the tree produces. Archon's YAGNI rule is explicit about not adding interface surface without a concrete accepted use case, and an inert contract field whose only producer lives in a fork is exactly that. If the backend never arrives, we own dead API forever and the next person to read `ExecutionContext` has to work out why half of it is unreachable. Kernel and backend arrive together, or neither does.

**Path remapping at the argv boundary is the wrong seam.** I put the detail in the #2207 review, so briefly here: engine path variables reach a node through two channels, and the PR only covers one. `$ARTIFACTS_DIR` is substituted textually into the node body before any docker argv exists, so the text carries the host path while the env bag carries the container path. Same variable, same node, two values, no error. On a `prompt:` node that is silent, because the agent is told in prose to write somewhere and does exactly that, inside the container, where the host never sees it.

Your own Definition of Done already lists the textual channel as unverified, so I do not think this is news. My worry is sequencing. Landing the env-only half first freezes the remap at a seam that cannot cover every channel, and every future path channel becomes another thing someone has to remember to remap.

The related problem is that `remapContainerPath` returns an unmapped value unchanged. On a same-path container that is right. On a relocated mount an unmapped engine-owned path is guaranteed wrong, and the failure is a write that looks like it worked. The engine sets `ARTIFACTS_DIR`, `STATE_DIR` and `LOG_DIR` itself, so it knows which keys must resolve, and a miss on those should throw and name the key.

### What would have to be true

Resolve the engine's path variables once, at run setup, when the execution context declares a mapping. Then every channel already carries the in-container path and there is only ever one value. That means the engine holds the host path and the in-node path as two named things rather than deriving one from the other with a prefix table at the edge, which is a type change worth designing deliberately. #2490 is already about naming the workspace port that implicitly exists, and this belongs there rather than beside it.

Do that, and `remapContainerPath` disappears from the arg builders. Only `-w workdir` stays, which is the part I have no argument with.

### One question that could make this much smaller

Does running Archon itself inside WSL solve your problem?

I ask because the mount divergence looks like a consequence of where Archon runs rather than something intrinsic. A Windows path and a Linux path can never be the same string, so same-path mounting is impossible for a Windows-native Archon talking to Docker in WSL2. If Archon runs on the Linux side, the paths match, the whole remapping problem stops existing, and what is left of your proposal is the container backend itself rather than a new addressing model.

If that works for you, this is a much smaller feature than it looks and it lands much sooner. If it does not work, I want to know why, because that reason is the actual justification for the addressing change and it belongs in the design.

### `direction.md`

Worth saying: `direction.md` currently has nothing at all about isolation scope, which is why this took a proposal to settle rather than a lookup. That is a gap on our side, not yours. I am going to write an isolation clause into it, and the answer here is what it will be based on.

### On #2207

Leave it open for now and tell me which you would rather do. Reshape it in place once the seam question is settled, or close it and open one PR carrying kernel and backend together. I do not have a preference, and it is your work, so it is your call. Either way the mechanical fix is worth knowing about: `packages/providers/src/exec-context.test.ts` is not listed in that package's `scripts.test`, so it never actually runs in CI, and #2603's guard now fails `bun run validate` because of it.

Thanks for running it in production first and for opening the proposal before the PR. That is the right order and it is the reason this was reviewable at all.
