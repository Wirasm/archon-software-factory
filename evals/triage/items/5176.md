# SQLite "database is locked" killed 24 workflow runs on v0.11.1 (Windows, concurrent detached runs): field data for #3786

Filed by seanrobertwright.

## Summary

Between 2026-10-13 and 2026-10-24 (UTC), SQLite `database is locked` errors killed 24 workflow runs on my install. All of them ran on **v0.11.1**, which predates the busy-retry fix in #3796 (which closed #3786). I upgraded to v0.12.1 on 2026-10-24 at about 22:08 UTC. In the first ~1.5 hours since, with two runs active, the logs show no `db.sqlite_busy_waiting` warnings.

I'm filing this as field data from Windows, with a sanitized log bundle attached. It shows more failure modes than #3786 records, and it leaves #3786's question about what holds the lock unanswered.

## What the logs show

- There are 1,823 `database is locked` log lines across 67 files (66 detached-run logs plus `serve.log`).
- 24 distinct runs were killed by a lock at least once. In the database, 12 of them reached `completed` only after being resumed, 9 are `failed` and 3 are `cancelled`. One run's log shows five invocations: the start and four resumes.
- Every lock line was logged while at least 2 and at most 7 Archon processes (`serve` plus detached runs) had log activity. These counts are lower bounds, because a process can be alive without logging.
- The worst day was 2026-10-20. Eight detached runs were launched within 73 s, starting at 09:50:01 UTC, and that day produced 968 lock lines.

### Failures that ended or blocked a run

1. **Node event write.** The error is `NodeEventWriteError: Could not persist node_started | node_completed | node_failed | node_skipped_prior_success for <node>: database is locked`, followed by `Workflow failed`. This is #3786's failure mode. Several of these came after the node's work had finished, for example `node_completed` for `implement.build`, `review__aggregate`, `pr-body` and `verify`.
2. **Terminal status write.** `workflow.terminal_status_write_failed` reports "Failed to persist terminal workflow status: Failed to fail workflow run: database is locked". This is the stuck-`running` case from the #3786 comments.
3. **Run never starts.** One run row records `Detached run failed to start: database is locked`. Three invocations died on `Failed to update conversation: database is locked` before a run row existed. In three cases, `cli.detached_startup_failure_record_failed` shows that the record of the startup failure was also lost to the lock.
4. **Resume fails.** `cli.workflow_resume_run_failed` and `workflow-resume-service` report "Failed to resume workflow run: database is locked". Once, the resume failed with "Cannot resume … failed to load prior run state".

## Is this fixed in v0.12.1?

From reading the source, I think it is. In v0.12.1, `SqliteAdapter` (`packages/core/src/db/adapters/sqlite.ts`) wraps every `query()` and `withTransaction()` in `retryWhileBusy`, which retries `SQLITE_BUSY` with no deadline. That should cover every write listed above. In v0.11.1 the adapter only sets `PRAGMA busy_timeout = 5000`.

## Open question

**What holds the write lock for more than 5 s?** #3786 asked this, and #3796 notes that each retry attempt still blocks the process's event loop for up to 5 s inside SQLite's busy handler. On this machine, between 2 and 7 processes passed the 5 s timeout often enough to log 1,823 lock lines in 11 days, so long lock holds are routine here, not a one-off load spike. On v0.12.1 these become waits instead of failures. I'll watch for `db.sqlite_busy_waiting` and add its `waitedMs` values to this issue. If v0.12.1 stays clean, feel free to close this as covered by #3796.

## Discussion


**Wirasm** (collaborator, 2026-10-26):

Thanks for the detailed write-up and the evidence bundle. It made this traceable.

Short version: this was mostly on Archon's side, and v0.12 fixed the main cause.

**What held the lock on v0.11.1.** Every event insert assigned `event_order` with `SELECT COALESCE(MAX(event_order),0)+1 FROM remote_agent_workflow_events`, and that column had no index. Each insert scanned the whole events table while holding the write lock. A scratch measurement gave about 43 ms per insert at 300k rows. With 2–7 processes streaming `hook_activity`/`tool_called` events, the lock was almost always held, and a waiter could lose for the full 5 s. Your logs fit: every `database is locked` comes at least 5.4 s after that process's previous log line, and most of the failed statements are event inserts. They were the victims, not the holders. v0.12 replaces that scan with a sequence table and an index (about 0.1 ms per insert), and adds the busy retry from #3796. That matches the clean logs you're seeing since the upgrade.

Your setup made it worse but didn't cause it. Eight detached runs within 73 s, a high hook-event rate and per-file cost on Windows all add load. Your pack looks ordinary.

**What's still on our side.** We found two places that can hold the write lock for seconds, and we'll fix them:
- When a run finishes, the transaction that writes its terminal status also lists every file in the run's artifacts directory. A large artifacts tree, for example one containing `node_modules`, holds the lock for a long time, and on Windows it's slower still. It also makes the terminal event row very large.
- Startup migrations take the write lock on every process start, even when there's nothing to migrate.

**If you can, two read-only checks would help confirm which of these mattered on your machine:**

```sql
SELECT count(*) FROM remote_agent_workflow_events;
SELECT event_type, length(data) FROM remote_agent_workflow_events
WHERE event_type LIKE 'workflow_%' ORDER BY length(data) DESC LIMIT 5;
```

Any `db.sqlite_busy_waiting` lines on v0.12.1, with their `waitedMs`, would help too. If they stay absent, we'll close this once the follow-ups land.
