# feat(workflows): bounded correction of invalid final JSON

Filed by daemons2000.

## Problem

An agent can finish useful work and still return final JSON that fails its schema. In our Codex/DeepSeek setup, a reviewer returned `evidence` as a string when the schema required an array. Archon's validator correctly rejected the answer, but the node failed without a correction attempt because the provider declared structured output as `enforced`.

Archon already has schema validation and bounded reasks for best-effort providers. The remaining question is how to recover from a final-answer formatting failure without repeating the original task or giving the correction access to tools.

## Why

Repeating a whole review costs time and may produce a different review. Adding formatter agents, reader scripts, or correction loops to each workflow also makes the workflow harder to maintain.

This seems worth handling once in Archon's final-answer path, with clear limits and provider support.

## Desired outcome

Allow a limited number of attempts to correct an invalid final JSON answer within the same node and session, using the work already completed. Corrections should have tools disabled and should not consume another workflow review round or loop iteration.

The public API and placement are open for discussion. We would like the design to fit Archon's roadmap, provider contract, and “YAML coordinates. Code computes. Agents judge.” approach.

## Acceptance

These are proposed outcomes for discussion:

- [ ] A schema failure can trigger a bounded final-answer correction without repeating the original task or tool use.
- [ ] The correction receives the rejected answer, schema, and precise validation errors.
- [ ] The retry limit is explicit and corrections can be disabled.
- [ ] Only schema-valid output advances the workflow; exhaustion or unsupported correction behavior fails clearly.
- [ ] Correction usage and answers remain observable within the original node.
- [ ] Existing behavior remains available, with a clear support contract across providers.

## Constraints and related work

- Keep schema validation strict. Our trial makes no automatic field conversions and does not attempt to prove that rewritten content has the same meaning.
- Keep provider-specific behavior behind the provider contract and avoid extra workflow nodes or scripts.
- Related: #1849 introduced validation and best-effort reasks; #3952 separated tool use from the final structured answer; #2848 discusses the provider runtime contract.
- We recognize that #3952 settled on provider/route handling without a new YAML key. The setting described below is an experiment, not a requirement for an upstream solution.

## Additional notes

We have implemented a local version in Archon's code, installed it in our own environment, and are continuing to test it. The original failure was observed on source revision `fbaac18896a05639431cfb8c58229113c4eb9c2a`, using DeepSeek through Codex with high thinking effort.

Our current approach is deliberately small:

1. Reuse the shared schema check and send validation errors back for a limited correction.
2. Have the provider resume the existing session with tools disabled, correcting only the final answer.
3. Stop when the answer passes or the correction limit is reached, retaining usage and output evidence.

The local trial uses `json_schema_retries: 2`, with `0` disabling corrections. Codex is our first implementation. The trial includes focused automated checks and small controlled DeepSeek tests; broader qualification is still in progress.

We would welcome discussion about making this more generic: whether the limit belongs on a node, in provider/route settings, or in an existing retry contract; how correction should fit the runtime contract; and how to support the maintained providers consistently.

If maintainers agree that this outcome fits Archon, we could prepare a PR later, adapted to the agreed design and current `dev`. This issue is a feature proposal and a request for feedback, not a request to accept our local implementation as-is.
