# Linear as the work-item tracker: a community forge plugin, and SDLC queues whose work items live apart from the code

Filed by schieble.

## Problem

The SDLC pack assumes a queue's `repo_host`/`repo_path` hold both the work items and the pull requests. A team that tracks its work in **Linear**, while its code, pull requests and CI stay on GitHub, can't run the pack:

- There is no forge plugin for Linear work items.
- Even with one, the pack would look for the code, the maintainer list and pull requests in the Linear "repository". It would expect GitHub to close the Linear issue on merge. And it would leave the Linear issue with no sign of the factory's work, because Linear has no forge cross-references.

## Why

Many teams keep their tracker apart from their code host. Linear is a common choice. The forge contract already separates hosts, so a work-item-only forge fits it. The gap is in the pack.

## Desired outcome

A queue can be pointed at a Linear team for its work items, while pull requests, CI and code stay in the checkout's GitHub repository. An issue filed in Linear is triaged, built into a pull request, merged and closed in Linear, with the factory's progress and questions visible on the Linear issue and no GitHub issue created.

## Acceptance

- [ ] A Linear forge plugin is installable with `archon plugin add` and serves every `workitem.*` and `repo.label*` operation the pack uses.
- [ ] With a queue's item location set to a Linear team, intake, the build queue and the merge queue read and write the Linear issue, and open, check and merge the pull request on GitHub.
- [ ] A merged pull request whose body says `Closes ENG-12` closes Linear issue ENG-12.
- [ ] The Linear issue shows each stage's progress and each question the factory asks.
- [ ] A project that moves from GitHub issues to Linear does not mix the two trackers' items.

## Constraints and related work

- Must remain true: projects whose work items are GitHub issues behave exactly as today.
- Related: we've published the plugin as a community forge plugin: `archon plugin add schieble/archon-forge-linear` (https://github.com/schieble/archon-forge-linear, MIT).
- Solution steering: **Hint.** This is what we did in our own copy of the pack. It has run end to end on a real product: a Linear issue went from filed to triaged, built, merged by the merge queue and closed in Linear in about 23 minutes, with no GitHub issue. The pack's existing suite passes unchanged (563 tests), plus 22 tests of ours.
  - **Item source.** A tracker-only item (host `linear.app`) is always read and written through `archon forge`, whatever `ARCHON_SDLC_FORGE` selects for the code forge, because `gh` can't reach it.
  - **Code repository.** When the item location is tracker-only, the default branch, the maintainer list and every pull request come from the checkout's single git remote; none or several refuse. This touches `fetchDefaultBranch`, `readMaintainerList`, `itemPullRequest`, the merge queue's base read and the build checkout.
  - **Work-item names.** A tracker-only item is `work/<team>-<n>` (`work/eng-12`; state names are lower case), and each queue claims and scans only items whose subject is in its own `repo_host`/`repo_path`. Without this, a project that moved from GitHub issues has its old `work/2` (GitHub #2) claimed for Linear issue 2. Our first live run hit exactly that.
  - **Maintainers.** `maintainers.json` entries may name a host, as in `{ "login": "alice", "host": "linear.app" }`. A tagged entry counts only on that host and an untagged one only on the code forge, so a Linear display name is never trusted as a GitHub login, nor the reverse.
  - **Closing.** After a merge, the merge queue's `retriage` node closes an open tracker-only item whose merged pull request's body closes it, before deciding on re-triage.
  - **Visibility.** Intake, the build queue and the merge queue each keep one progress comment per stage on a tracker-only item, replaced in place. Each attention question gets its own comment with how to answer it.
  - **Prompts.** Agents are told how to read a Linear item (`archon forge workitem.view` / `workitem.comments`) and how to reference one in a pull request (`Refs ENG-12`, `Closes ENG-12`, never `#12`).
  - **Own-PR enrollment** is refused for tracker-only items, since an own pull request's work item is named by its PR number.

## Additional notes

**The plugin.** `forge-linear` claims host `linear.app`. A Linear team stands where a repository would: issue `ENG-12` is `{ "repo": { "host": "linear.app", "path": "<workspace-url-key>/ENG" }, "number": 12 }`. It refuses a `pr` subject.

- **Operations:** `workitem.view`, `workitem.comments`, `workitem.list`, `workitem.create`, `workitem.labels.set`, `workitem.label.add`, `workitem.label.remove`, `workitem.comment.upsert`, `workitem.close`, `workitem.edit-body`, `repo.labels.list` and `repo.label.ensure`. The key comes from `LINEAR_API_KEY` through `token_env`.
- **State.** Triage, backlog, unstarted and started issues are open; completed and canceled ones are closed. A close goes to the team's completed state, a canceled state named like "Duplicate", or another canceled state. Closing an issue already closed for another reason is a `conflict`.
- **Labels** are team plus workspace labels, with groups left out. Adds and removes use Linear's single-label mutations, so a concurrent writer's label survives.
- **Authors.** `login` is the Linear display name, which is unique in the workspace.
- **Tests:**
  - 42 handler tests against an in-memory Linear. Every response is parsed with `forgeResponseSchema` and checked with `matchesForgeOperationResponse`.
  - A live probe runs every operation through `archon forge` against a real team. It passes 13 of 13 with the released binary installed by `archon plugin add`.

**One contract question: Linear rewrites description Markdown.** It adds a blank line after the first line, turns `-` bullets into `*`, writes `[x]` as `[X]`, links bare URLs, escapes some characters and collapses repeated blank lines. The first line (where the pack keeps its `<!-- marker -->`) survives, and comments are stored byte for byte.

So the plugin counts a description write as `applied` when a fresh read returns exactly the text Linear answered the mutation with. The `bodyDigest` it reports is the digest of the **requested** text, which is what the host's matcher checks, not of the bytes Linear holds. If you'd rather the contract model "the forge normalizes the body", we'll follow whatever shape you choose.

**Questions for the maintainers:**

1. Would you list `forge-linear` as a community forge plugin (for example in the forge reference), or take it into `plugins/`?
2. Do you want "work items in a tracker apart from the code repository" in the pack? We can reshape the hint above however suits you.
3. Is the description-digest approach acceptable, or should the contract say how a forge that normalizes bodies reports a write?
