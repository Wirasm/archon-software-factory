# PostgreSQL liveResourceSlotHolders query fails with invalid input syntax for type uuid when heterogeneous slot holders exist

Filed by codeCraft-Ritik.

## Problem

In `packages/core/src/db/resource-slots.ts:114-123`, `liveResourceSlotHolders()` executes a `DELETE` cleanup query casting `remote_agent_resource_slot_holders.holder_id` directly to `UUID`:
```sql
DELETE FROM remote_agent_resource_slot_holders
 WHERE resource_key = $1 AND holder_kind = 'run'
   AND NOT EXISTS (
     SELECT 1 FROM remote_agent_workflow_runs w
      WHERE w.id = CAST(remote_agent_resource_slot_holders.holder_id AS UUID)
        AND w.status NOT IN ('completed', 'failed', 'cancelled')
   )
```
In PostgreSQL, the query planner does not guarantee that `holder_kind = 'run'` evaluates prior to `CAST(holder_id AS UUID)`. When the table contains rows with `holder_kind = 'attempt'` (or other non-UUID holder IDs, such as provider attempts), PostgreSQL crashes with:
```text
ERROR: invalid input syntax for type uuid: "..."
```
This fails the scheduler tick transaction and prevents slot acquisition.

## Why

`liveResourceSlotHolders` is executed on every scheduler tick and whenever any workflow run or provider query attempts to acquire or verify resource slots. A crash in this query prevents resource slot allocations across the entire system, halting workflow admissions and provider operations on PostgreSQL deployments.

## Desired outcome

The cleanup query should safely handle non-UUID `holder_id` values regardless of PostgreSQL query planner predicate ordering, ensuring that `CAST(... AS UUID)` is never evaluated on incompatible string values.

## Acceptance

- [ ] `liveResourceSlotHolders()` completes successfully when `remote_agent_resource_slot_holders` contains non-UUID strings in `holder_id` (e.g. `holder_kind = 'attempt'`).
- [ ] Expired run holders are still purged as expected when their associated workflow runs become terminal or are deleted.
- [ ] PostgreSQL integration tests pass with heterogeneous holder records in the same resource slot.

## Evidence

### Reproduction

1. Configure Archon with a PostgreSQL database (`ARCHON_DATABASE_URL=postgres://...`).
2. Insert a resource slot holder with `holder_kind = 'attempt'` having an arbitrary non-UUID string ID:
```sql
INSERT INTO remote_agent_resource_slot_holders
  (resource_key, holder_kind, holder_id, owner_host, owner_pid, acquired_at)
VALUES
  ('shared_slot', 'attempt', 'worker-attempt-9876', 'localhost', 1234, NOW());
```
3. Call `liveResourceSlotHolders(query, 'shared_slot')`.
4. PostgreSQL throws:
```text
error: invalid input syntax for type uuid: "worker-attempt-9876"
```

### Environment

- Archon version or commit: `ca45f0d43` (dev branch)
- Platform or adapter: All adapters using PostgreSQL
- Database: PostgreSQL (14, 15, 16)
- OS: Linux / macOS / Windows


## Constraints and related work

- Must remain true: The query must keep `w.id` as a bare column in the subquery so that PostgreSQL can use the primary key index on `remote_agent_workflow_runs(id)`.
- Solution steering: Hint — Wrap the cast in a conditional `CASE WHEN remote_agent_resource_slot_holders.holder_id ~* '^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$' THEN CAST(remote_agent_resource_slot_holders.holder_id AS UUID) ELSE NULL END`. In PostgreSQL, `CASE` expressions guarantee that the `THEN` clause is not evaluated if the condition is false.

## Additional notes

PostgreSQL official documentation on [Expression Evaluation Rules](https://www.postgresql.org/docs/current/sql-expressions.html#SYNTAX-EXPR-EVAL) states:
> *"The order of evaluation of subexpressions is not defined. In particular, the inputs of an operator or function are not necessarily evaluated from left to right or in any other fixed order... When it is essential to force evaluation order, use a CASE construct."*
