# A project can load workflows from a git ref of its own repository

Filed by andras-tkcs.

## Problem

Archon reads project workflows only from the checked-out `.archon/workflows/` folder, plus bundled, global and installed-pack scopes. A repository that keeps its workflows on a dedicated branch (for example per-feature implementation plans on a `plans` branch, kept out of `dev` history) cannot use them: the branch is never read.

The two obvious workarounds both fail:

- Registering the same repository a second time, checked out on that branch, is refused because the repository URL is already registered.
- Global scope (`~/.archon/workflows/`) loads for every project, but plans and their workflows are per repository. With many repositories, each with its own plans, global scope mixes them all together.

Even with a way to read the branch, a stale local copy is a risk: a plan pushed to the branch is not visible until something refreshes it, and there is no operator-facing way to do that.

## Why

Plan-then-implement is a core Archon flow. Teams that review a plan before implementing it want the plan, and the workflow that executes it, in version control next to the code but separate from the code branch. Today that means copying files between branches by hand, or keeping a second registration that Archon refuses.

## Desired outcome

- A project can name additional workflow sources by git ref of its own repository, and discovery lists their workflows like project workflows.
- Runs that use such a workflow stay frozen like any other run: the source is captured at run start, and a push to the ref during or after a run never changes that run or its resume.
- An operator can refresh the ref explicitly (CLI, API and Web UI) and can see which commit a project last synced.

## Acceptance

- [ ] With a ref configured, a workflow that exists only on that ref appears in `archon workflow list` and can be run.
- [ ] A push to the ref after a run has started does not change that run's behavior, including after resume.
- [ ] A configured ref that does not exist, or a path that is not in it, fails with an error that names the ref and path. It does not fall back to stale or project-only content.
- [ ] An explicit sync updates what the next run uses, and the commit in use is visible to the operator.
- [ ] Nothing fetches or mutates the user's checkout in the background, and the user's working tree and current branch are never switched.
- [ ] A project that configures nothing behaves exactly as before.

## Constraints and related work

- Must remain true:
  - A run's executable source is its capture, verified by digest on resume.
  - Configuration is read from the project's own checkout, not from the ref it points to.
  - No new YAML workflow field.
- Scope boundary: workflows, commands and scripts read from a ref of the same repository. Other repositories and private-repository auth are out of scope. Event-driven refresh (webhooks) is out of scope; it is a caller of the explicit sync.
- Known prerequisites or blockers: the capture manifest records its scopes, so a new scope needs a manifest revision that keeps older captures readable.
- Related issues or PRs: none found.
- Solution steering: Hint, not requirement. Something like a `workflows.extraSources: [{ ref, path }]` entry in `.archon/config.yaml`, loaded as a scope between global and project and captured with the others, with a sync operation that fetches the configured refs. Reading the ref's tree from git without a checkout would keep the working tree untouched. Another shape that meets the acceptance list is fine.

## Additional notes

I am willing to implement this and would like direction on two choices before starting: whether a run should fetch the ref implicitly (I lean no: explicit sync only, matching "nothing updates in the background"), and whether the scope belongs between global and project or should rank differently against project workflows of the same name.


## Discussion


**Wirasm** (collaborator, 2026-11-11):

Thanks for the clear write-up. Before adding a new workflow source to the engine, here's how this works with what Archon already has.

Keep the plans branch in its own worktree and point the run at it:

```
git worktree add ../plans plans
archon workflow run <workflow> --workflow-source ../plans
```

Run it from your project checkout. `--workflow-source` reads the workflow, its commands and its scripts from that directory's `.archon/workflows`, `.archon/commands` and `.archon/scripts`, while the run still acts on the checkout you launched from (and reads its `.archon/config.yaml`). See [Running a workflow from another checkout](https://archon.diy/reference/cli/#running-a-workflow-from-another-checkout). To pick up a new push, `git -C ../plans pull`. A run that already started is unaffected, because the run captures its source when it starts.

A second suggestion: treat a plan as an input to a run rather than as a workflow. One generic "implement this plan" workflow can take the plan as a file or a message (for example `archon workflow run <workflow> "Implement ../plans/feature-x.md"` or a declared `--input`). Then the plans branch holds only plans, and nothing per plan needs to be discovered as a workflow.

If neither covers your case, say what's missing and we'll take it from there. I've closed #5375 with the reasoning.
