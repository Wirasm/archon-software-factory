# Projects that span several git repositories (nested, microservice, multi-repo)

Filed by semiholectus.

This started as a user question (nested git repositories under a git workspace root) and is now a design issue. The maintainer wants Archon to support projects that span several git repositories, whether nested, microservice or multi-repo. The shape is not decided, so this lists the problem, the options and the constraints, and ends with the questions that have to be answered first. It deliberately has no acceptance criteria or implementation steps.

## Problem

Many real projects are not one repository. Examples that keep coming up:

- A workspace repo holding shared AI config (`CLAUDE.md`, `.agents/`, `.archon/`) with the real code in nested repos under a gitignored directory:
  ```
  /workspace              git repo (shared config)
  └── repositories/       gitignored in /workspace
      ├── repository-1    its own git repo and remote
      └── repository-2    its own git repo and remote
  ```
- A non-git parent folder holding N service repos (a microservice platform).
- A set of sibling repos that change together (a service and its shared library).

Archon models a project as one repository (a worktree per run) or one non-git folder (run in place). A layout that mixes git levels, or a change that must touch several repos with isolation and pull requests per repo, does not fit either cleanly.

## Why it matters

The reporter wants to use Archon as a daily driver on this layout, and a cross-service change ("bump a shared package in all services") is a common job. Today the options below each give up something: isolation, per-repo pull requests, or the shared configuration.

## What works today

- **Folder project**, for a non-git root. `archon workflow run --folder` registers the root, the run executes in place at that root, and the agent sees every contained repo. Container isolation with a write-back gate exists for folder projects. There is no worktree, no managed branch or pull request: the agent runs git itself in each repo. See the Multi-Repo Projects guide.
- **Repo project per repository.** Each nested repo can be registered on its own and gets a normal worktree and PR flow. A nested repo resolves to its nearer git top level, not to the parent, since #3553 and #3650.
- **Not supported:** a git repo as the workspace root with nested repos beneath it. It registers as a repository project, and a run in a worktree of that repo does not contain the gitignored nested repos (a worktree checks out tracked files only), so the nested code is absent.
- A cross-repo group command (`archon group register`, #1349) and codebase tags with a `services:` field (#1348) were closed in favor of folder projects, to avoid a competing cross-service schema.

## Shapes on the table

These are options to compare, not a decision.

1. **Extend folder projects to a git root.** A git repo registered as a folder project, running in place with the nested repos visible. Smallest change; keeps the "agent does per-repo git" model and gives up isolation and managed PRs at the root.
2. **A composed multi-repo workspace.** One run gets a worktree per member repo under one root, as a new workspace backend. This is what the Multi-Repo guide calls a possible future isolation backend, and it fits the workspace idea in direction.md (a worktree is one way to provide a workspace) and the Workspace port proposed in #2490. Gives isolation and per-repo branches; largest design.
3. **Fan-out over repo projects.** A parent run starts one child run per registered repo project (dynamic `workflow:` fan-out, #2224), each with its own worktree, branch and PR, and the parent joins the results. Composes existing primitives and respects "runtime-created independent work belongs in a child run"; needs a way to name the set of repos.
4. **Shared configuration only.** Keep one project per repo and solve just the shared-config part (the `CLAUDE.md` and `.agents/` in a parent repo) through user-level or layered config. Does not address cross-repo changes.

## Constraints from the current code and direction

- A codebase row has `kind: 'repo' | 'folder'`, chosen at registration by whether a git root exists (orchestrator-agent project registration). A git-root workspace therefore becomes `repo` today.
- A folder project rejects `--branch`, `--from` and `--base`, and reports `/worktree` as not applicable.
- Schema changes are additive only; there is no migration ledger. A new project kind or a membership table must stay valid for older binaries.
- The engine never infers isolation (direction.md); anything that creates worktrees across repos is selected explicitly.
- Execution is the outer boundary and the workspace nests inside it (direction.md); a multi-repo workspace must work inside a container run.
- Archon stays small: avoid a competing cross-service schema (the reason #1348 and #1349 were closed) unless it clearly beats composing existing pieces.
- Several clones of one remote are a separate problem (#1192) with its own identity question.

## Open questions

1. Is the unit a project that contains repos (a root, with membership discovered or declared), or a set of independent repo projects that a run is pointed at?
2. Who owns git for the member repos: the agent (today's folder model), or Archon (worktree, branch and PR per repo)?
3. Is isolation required for the cross-repo case, or is run-in-place plus the container overlay enough?
4. How is membership declared: discovered from the filesystem, listed in config, or registered one repo at a time?
5. What is a run's single result when several repos change: one pull request per repo, linked runs, or a parent run that aggregates?
6. How does shared configuration (guidance files, `.archon/`) reach each member repo without copying or symlinking?
7. Does a git-root workspace need its own kind, or is "folder" about running in place rather than about git absence?

## Discussion


**Wirasm** (collaborator, 2026-10-04):

Answering the original question honestly. There is no `archon group register`; #1349 was closed in favor of folder projects. Folder projects cover only non-git roots today (`archon workflow run --folder`, run in place at the root). Your layout, a git repo at `/workspace` with gitignored nested repos beneath it, is not supported: `/workspace` registers as an ordinary repository project, and a run in a worktree of it will not contain `repositories/`, because a worktree holds tracked files only. What does work now: register each nested repo as its own project (a nested repo resolves to its own git top level), or move the shared config to a non-git parent and register that as a folder project.

The maintainer wants Archon to support this class of setup: nested git repos, microservice and multi-repo projects. The shape is not decided yet, so I retitled this as a design issue and rewrote the body with the options and open questions. If you can say how you would want a run to behave across `repository-1` and `repository-2` (one branch and PR per repo, or one change set), that is exactly the input the open questions need.
