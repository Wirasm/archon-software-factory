# feat(orchestrator): pin an available workflow to a project or channel

Filed by hidegh.

Part of #2836. Updated for the approved instance-installed plugin model (22 September 2026).

Depends on #2835. The conversation/channel form also depends on #2786.

## Problem

A registered project or intake channel may have one deterministic workflow that should receive ordinary messages. Today the operator must either rely on agent routing or repeat an explicit workflow-run command for every message.

The use case is valid, but a global project-name-to-workflow-name table is the wrong foundation:

- it bypasses project workflow availability;
- project and workflow names are weak install-level identifiers;
- it applies an intake-channel behavior to every conversation bound to the project;
- it creates another workflow-discovery path;
- a configurable text prefix turns natural language into a control protocol.

## Outcome

Allow an operator to pin one workflow that is already available in the effective project workflow catalog.

Two scopes are supported:

1. **Project default** — applies when a project-bound conversation has no more specific pin.
2. **Conversation/channel pin** — applies to one platform-neutral conversation/channel binding and overrides the project default.

Routing precedence:

```text
explicit command or active gate
  → conversation/channel pin
  → project default
  → agent run management/router
```

A pin selects the destination deterministically. It does not change workflow permissions, isolation, inputs, execution, or reporting.

## Ownership

### Workflow target

Resolve the target through the project-scoped catalog from #2835. A pin cannot reference a workflow unavailable to that project.

Use the catalog's typed plugin/pack and public-workflow identity/owner. A pack being installed is insufficient: the target must be exposed for this project. Internal supporting workflows are not pinnable unless declared public and enabled. Selection never installs a partial pack or creates another installation record. Do not create a second case-insensitive project-name-to-workflow-name resolver.

### Project default

Store project policy against the registered project's stable identity, in the same project-settings ownership boundary used by the pack policy. Repo-kind and folder-kind projects must behave consistently.

### Conversation/channel pin

Use Archon's shared conversation/origin model rather than adding per-adapter dispatch implementations.

The portable channel form depends on the normalized adapter/channel identity from #2786. Adapters supply identity; core owns routing policy.

### Execution

Reuse the existing explicit workflow-run path after the pin has resolved. Listing, validation, parse warnings, inputs, approval behavior, isolation, and errors must remain identical to an explicit run.

Do not rediscover all workflows inside the dispatch path.

## Operator control

Config and CLI must expose the same policy:

- inspect the effective project default and any conversation/channel override;
- set a pin only to a currently available workflow;
- remove a pin explicitly;
- explain which scope produced the effective pin.

A structured command or UI action may bypass/remove a pin or route one message to chat. Do not add a configurable sigil/prefix that code parses from ordinary prose.

## Failure behavior

- An unavailable or removed target fails clearly and runs nothing. A plugin update or removal must not silently retarget the pin to a different workflow identity.
- Do not silently fall through to agent routing when a configured pin is invalid.
- Explicit slash commands continue to win.
- An active approval/input gate continues to win.
- A conversation without a pin and a project without a default behave as before.
- Detaching or rebinding a conversation must not leave an invisible stale effective pin.

## Definition of done

- [ ] A project can have one default workflow selected from its #2835 catalog.
- [ ] A conversation/channel can have one override selected from the same project catalog.
- [ ] Effective precedence is explicit command/gate, then conversation/channel, then project, then agent routing.
- [ ] Project policy uses stable registered-project identity rather than name guessing.
- [ ] Channel policy uses #2786 structured origin and no adapter-specific dispatch branch.
- [ ] Config and CLI inspect, set, and remove the same policy.
- [ ] Invalid or unavailable targets fail visibly before isolation or provider cost.
- [ ] The normal explicit run path executes the resolved workflow.
- [ ] Parse warnings, declared inputs, attachments, gates, isolation, and result reporting match explicit execution.
- [ ] No new workflow discovery path is introduced.
- [ ] No natural-language prefix, regex, or sigil controls dispatch.
- [ ] Unconfigured projects/conversations preserve current behavior.
- [ ] Focused tests cover precedence, project isolation, unavailable targets, gate priority, rebind/detach behavior, and every supported adapter through the shared seam.
- [ ] Configuration and CLI documentation explain scope, precedence, failure behavior, and the explicit escape action.

## Boundaries

- No workflow-pack publication or installation; #2767 owns distribution.
- No pack activation or availability resolver; #2835 owns the project catalog.
- No new workflow YAML field such as `trigger:` or `binds_to:`.
- No changes to workflow permissions or provider capabilities.

## Prior implementation

PR #2541 proved the deterministic-dispatch use case and the shared run-path handoff, but it predates the pack/catalog direction and uses the superseded global mapping and prose-bypass primitive. That PR should not be rebased again; implementation should start from current `dev` after the dependencies above.
