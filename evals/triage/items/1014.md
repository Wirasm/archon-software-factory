# feat(web): inspect individual loop iteration output and tool activity

Filed by coleam00.

## Problem

The console run detail page shows that a loop ran, but not what each iteration did. `RunGraphPanel` marks `loop` nodes with a glyph (`packages/web/src/experiments/console/components/RunGraphPanel.tsx`) and the run stream (`RunStream.tsx`) is organised by node, so an operator cannot select iteration 3 of a loop and read its output and tool calls. PR #1026 delivered the count, live progress and per-iteration status and duration in the legacy UI, which no longer exists. The console has none of it yet.

## Why it matters

Loops are where runs converge, stall or burn money. When a convergence loop ends after eight iterations, the operator needs to see what iteration 5 produced to know why it did not finish. The same need applies when auditing a resumed run. This covers both single-node `loop` and multi-node `loop_group`, where the same body node id repeats once per iteration.

## Desired outcome

On the console run detail page, each loop iteration can be inspected on its own.

- Expanding a loop shows its iterations with status and duration, plus current and maximum iteration count while the run is live.
- Selecting an iteration scopes the stream to the output and tool activity attributed to that iteration.
- For a `loop_group`, body-node activity appears under the right group and iteration. The same body node in two iterations is never conflated.
- Live view and persisted history use the same iteration identity (see #2090, iteration-tagged loop-group body events).

## Invariants

- This reads already-recorded execution history. It does not change loop scheduling or execution semantics, and does not introduce cyclic scheduling.
- The console consumes the generated API types and the existing run event stream; it adds no import from server or workflow runtime packages.
- Persisted run history is the source of truth, not client-only streaming state.

## Acceptance

- Selecting an iteration shows that iteration's output and tool calls, and nothing from other iterations.
- Two executions of the same body node in different iterations can be inspected independently.
- The view is identical after a page reload and after a workflow resume, not only while events stream.
- Count, status and duration remain visible in the compact view.
