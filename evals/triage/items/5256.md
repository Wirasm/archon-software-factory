# auth-service: session cookie never expires server-side and survives credential changes

Filed by Quinnod345.

### Problem

The form login sidecar issues the same session cookie for every login and `/verify` never expires it.

- `handleLogin` sets `signCookie('authenticated')` (`auth-service/server.js:180`).
- `handleVerify` accepts any cookie where `verifyCookie(...) === 'authenticated'` (`auth-service/server.js:145-146`).

`Max-Age=${COOKIE_MAX_AGE}` (`auth-service/server.js:183`) only tells the browser when to drop the cookie. A copied `archon_auth` value keeps passing `/verify` for as long as `COOKIE_SECRET` stays the same. Changing `AUTH_USERNAME` or `AUTH_PASSWORD_HASH` does not end existing sessions either.

### Reproduction

Start the sidecar with any `AUTH_USERNAME`, `AUTH_PASSWORD_HASH` and `COOKIE_SECRET`, then build the cookie by hand in a shell that has the same `COOKIE_SECRET` exported:

```sh
COOKIE=$(node -e "const {createHmac}=require('crypto');console.log('authenticated.'+createHmac('sha256',process.env.COOKIE_SECRET).update('authenticated').digest('base64url'))")
curl -s -o /dev/null -w '%{http_code}\n' -H "Cookie: archon_auth=$COOKIE" http://127.0.0.1:9000/verify
```

This prints `200` no matter when the cookie was made or whether the username or password hash changed since.

### Expected

`/verify` rejects a session once `COOKIE_MAX_AGE` has passed since login, and rejects existing sessions after the username or password hash changes.

### Suggested fix

Sign an expiry and a short credential fingerprint into the payload (`authenticated.<exp>.<fingerprint>`) and check both in `/verify` after the existing signature check. Existing sessions would be logged out once on upgrade.
