# feat: abort running chat responses (AbortSignal + /cancel endpoint + Stop button)

Filed by fcamblor.

## Problem

In console chat, once a message is sent there is no way to stop the in-flight response. `ChatComposer.tsx` only disables input while the assistant works (`disabled`, `disabledReason`); neither it nor `ChatStream.tsx` has a stop control. The server has no conversation-level cancel: the only cancel is run-level (`/api/workflows/runs/{runId}/cancel`, `packages/server/src/routes/api.ts`), and no `AbortSignal` reaches the provider from the orchestrator.

## Why it matters

A wrong prompt or a runaway generation keeps running and keeps costing money until it finishes. The only escapes today are waiting, or `/reset`, which throws away the conversation context. Closing the tab does not help: generation continues server-side and is still billed.

## Desired outcome

An operator can stop an in-flight chat response from the console, keep the conversation, and send a refined message.

## Invariants

- Stopping aborts the provider call, so spend stops. Hiding the output in the UI does not count.
- Partial output already streamed is kept and marked interrupted. The conversation stays usable.
- A stop that races with normal completion is harmless and idempotent.
- An abort is not reported as an error to the operator.
- Cancel authority matches the existing `/message` endpoint's auth.
- Provider-specific abort handling stays inside `@archon/providers`; the orchestrator passes a signal through the provider contract, so Claude, Codex and Pi behave the same.
- This is for operator chat only. Run-level cancel is unchanged.

## Acceptance

- During a response, the composer shows a Stop control; clicking it ends the response within a short time and returns the composer to idle.
- After stopping, the provider call is verifiably aborted (no further tokens or spend).
- The partial message remains in the stream, marked as interrupted, and survives a reload.
- The next message in the same conversation works with prior context intact.
- Stop when nothing is in flight does nothing and does not error.

## Context

The original requester (fcamblor) linked a working proof of concept on `feat/cancellation-in-chat` (an abort controller per conversation in the lock manager, a cancel endpoint and an SSE event). It was written against the legacy UI. It is useful prior art for the server half, not a constraint.

**kindrat86** (none, 2026-08-11):

The inability to abort an in-flight AI response is not just a UX issue — it is a cost control gap. If an agent enters a long generation loop or starts processing a massive context window, the only way to stop the spend is to wait for it to finish.

An abort/stop button is the right UI pattern, but it is reactive — you can only stop what you can see. The complementary approach is preventive: evaluate each API call against spend rules before it starts executing.

AgentShield does exactly this. A per-transaction spend firewall that evaluates each call in under 1ms:

- **transaction_limit**: Block calls over $X (catches expensive model calls before they start)
- **session_budget** (new): Session-scoped spend cap with decay tightening — as the session spends more, per-call thresholds shrink, preventing the "death by a thousand cuts" pattern
- **velocity**: Detect and block burst patterns (>N calls in Y minutes)
- **cascade_cost** (new): Estimates expected cost including retry probability × reversal cost

Pure Python 3.11 stdlib, zero dependencies. The abort button catches runaway responses; AgentShield prevents them from starting.
