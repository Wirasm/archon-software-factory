# A dropped trigger fire shows up on the attention stream

## Problem

When `archon trigger fire` reaches a binding whose resource is full and the binding's `overlap` is `skip`, the engine stores the start as `skipped` and never reads it again (`packages/core/src/db/resource-starts.ts:114`; the drain reads only `queued`, `packages/core/src/db/resource-slots.ts:250-253`). Nobody watching the attention stream learns of it. The receipt says `matched` with an empty `reason`. If the fire came from a run as its hand-off, that run has usually ended by then, and the work it handed off waits until a person notices.

The engine knows everything needed to say so: the receipt names the binding, the resource, the blocking run (`blocker_run_id`) and, for a fire from inside a run, the firing run (`source_actor` is `{"source":"archon-run","id":...}`).

## Evidence (one install, dogfood 2026-11-12, 00:56 to 08:05 UTC)

- 15 of 40 build hand-off fires and 13 of 13 merge hand-off fires were skipped (start requests joined to their receipts; fires counted as receipts with a delivery id).
- The build waits that followed totalled 340 minutes, up to 88 minutes for one item, median 20.
- The attention watch carried 33 asks and 147 notices that night. None of the 28 skipped fires appeared on it. The operator found each one by reading state.

## Why it matters

The attention stream is the one place an operator, or an agent acting for one, watches to learn what needs them. A dropped hand-off is the single largest silent wait the dogfood measured, and it is invisible there. Fixing overlap per start kind (issue 5508) will make dropped fires rarer, but a fire can still be dropped by a binding that keeps `skip` for fires, and a scheduled tick under `skip` is dropped by design.

## Why now

Hand-offs by `archon trigger fire` are now the normal way queue workflows chain: an answered question fires the next round, a Ready build fires the merge sweep. Each new hand-off adds another place a drop can hide.

## Desired outcome

A skipped start that came from an explicit fire (a start with a delivery id) produces one notice on the attention stream, visible with `archon workflow attention --notices` and on `--watch --notices`. The notice names the binding, the resource and the blocking run or request, and says the start was dropped rather than queued. When a run made the fire, the notice belongs to that run, so it is listed with the run's other notices even after the run ended.

## Invariants

- Engine-general. The notice text and labels come from facts the engine owns: binding id, resource key, overlap policy, blocker, delivery id. The engine never reads the fire's inputs as meaning, and knows nothing of SDLC items, stages or queues.
- One notice per skipped fire, at most. A retried fire with the same delivery id that hits the existing request adds none.
- A scheduled tick skipped under `skip` produces no notice: that drop is the policy working, and a 5-minute schedule would flood the stream. It stays visible through the receipt and `archon trigger inspect`.
- A notice asks nothing and holds nothing: it never pauses a run, takes a slot or becomes an ask.
- Notices keep their existing bounds (`WORKFLOW_NOTICE_LIMITS` in `packages/workflows/src/workflow-notice.ts`).
- Additive only: no column renamed, retyped or dropped.

## Acceptance

- A test fires a binding with capacity 1 and `overlap: skip` while the slot is held, from a run, and sees one notice under the firing run naming the binding, the resource and the blocker.
- The same fire made from the CLI with no firing run produces a notice the stream lists under the binding's project.
- A scheduled tick skipped the same way produces no notice.
- A repeated fire with the same delivery id produces no second notice.
- `archon workflow attention --notices --since 24h --json` lists the notice with the same shape as other notices.

## Not in this issue

"An item waits and nothing will claim it" is a queue fact, not an admission fact. The engine sees only starts, not the items a workflow keeps in its state. Detecting an item that stayed unclaimed after its hand-off was dropped belongs to a future queue primitive that owns items and their claims. This issue gives that primitive the signal it would build on; it does not reconstruct item state.

## Solution steering (optional)

Two shapes fit, and the build should pick the smaller after reading the notice reader. Write a `workflow_notice` event on the firing run at the moment the start is stored as skipped. Or have the notice reader also read skipped fire requests from `remote_agent_resource_start_requests`, which already stores everything the notice needs, so nothing new is written. The second needs the live `--watch` stream to see those rows too.
