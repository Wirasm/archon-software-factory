# Trigger bindings need different overlap for scheduled ticks and explicit fires

## Problem

A binding's `overlap` policy applies to every start of that binding, whatever started it. A queue binding needs two different behaviors at once:

- A scheduled tick that arrives while the resource is busy should be dropped: the next tick does the same work.
- An explicit `archon trigger fire` (a hand-off: an answered question, a follow-up round) that arrives while the resource is busy should wait and then run, because nothing else will do that work until the next tick.

With `overlap: queue`, scheduled ticks pile up without bound and without deduplication. With `overlap: skip`, hand-offs are silently dropped.

## Evidence (one install, 2026-11-11)

- A merge-queue binding with `overlap: queue`, capacity 1 and a 30-minute schedule held 28 queued starts, the oldest 12 hours old, with 24 more already withdrawn. Each queued sweep that finds a waiting pull request runs an agent (about 60 s and 238k input tokens) to repeat a "wait".
- A build-queue binding with `overlap: skip` and capacity 2 dropped 2 of 5 follow-up fires because both slots were busy.
- With `skip`, a fire made from inside a run that holds the resource's only slot is always dropped: a `merge` answer's follow-up sweep never starts and the item waits for the next tick.

## Why it matters

A pack author has to choose between burning runs on stale queued ticks and losing hand-offs. Neither is a pack decision; it is admission behavior every queue-shaped workflow needs.

## Why now

The SDLC pack's time from ready to merged is dominated by waiting for the next sweep. Shortening a schedule makes the `queue` pile-up worse and the `skip` loss more frequent.

## Desired outcome

One binding can say that scheduled starts do not accumulate while explicit fires are kept. Queued work for one binding is bounded.

## Invariants

- Existing binding files keep their current behavior unless they opt in.
- Capacity and resource admission are unchanged.
- No schema column is renamed, retyped or dropped.

## Acceptance

- A scheduled tick arriving while an identical scheduled start is already queued or running for that binding adds nothing to the queue.
- A fire with a delivery id arriving while the resource is busy is admitted when a slot frees.
- `archon trigger list` or `inspect` shows why a start was dropped or merged into an existing one.

## Possible shapes (not decided)

Overlap per start kind (`schedule: skip`, `fire: queue`); or `queue` that coalesces starts with equal inputs; or a bound on queued starts per binding.
